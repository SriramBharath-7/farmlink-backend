## What was built

- `db/models.py` — SQLAlchemy declarative models for the full blueprint
  schema: `users`, `fpos`, `farmer_profiles`, `fpo_members`,
  `buyer_profiles`, `commodities`, `markets`, `market_prices`,
  `buyer_demands`, `lots`, `lot_images`, `quality_grades`, `offers`,
  `transactions`, `payments`, `logistics_providers`,
  `cold_storage_facilities`, `logistics_bookings`, `grievances`,
  `audit_logs` — 19 tables plus Alembic's own `alembic_version`.
- `migrations/` — Alembic setup, two revisions:
  - `e2dd6d9a2b45_initial_schema.py` — the full schema above, autogenerated
    from `db/models.py` against a real empty Postgres 16 database (not
    hand-typed DDL that could drift from the ORM models).
  - `0002_transaction_state_machine_trigger.py` — a Postgres trigger
    function enforcing the blueprint's transaction state machine
    (section 28: "must never jump randomly between states") at the
    database layer, not just as an application-layer convention.
- `db/session.py` — engine/session factory reading `DATABASE_URL` from
  the environment; no hardcoded credentials anywhere.
- `db/seed_from_json.py` — loads the project's existing
  `data/buyers_augmented.json`, `data/mock_mandi_prices.json`,
  `data/logistics_providers.json`, `data/cold_storage.json` into the new
  tables, tagging every row's provenance explicitly (`SYNTHETIC` for all
  of it, since none of these files are live-sourced yet — see point 3
  below and `AUDIT_REPORT.md`'s existing e-NAM/data.gov.in notes).
- `tests/test_db_schema.py` — 14 new tests (see "What was actually
  tested" below).

## Documented deviations from the blueprint doc, and why

The blueprint's "Core Database Schema" section only gives full
column-level detail for `users` through `quality_grades`. `offers`,
`transactions`, `payments`, `logistics`, and `grievances` are named in
the architecture diagram but never given schemas in the doc — those five
were designed from the blueprint's *prose* (sections 12, 18-19, 21,
28-29) and from the deterministic core's actual tested output shapes,
not copied verbatim from a schema that doesn't exist in the source
document. Specifically:

- **`grievances.complaint_type`** uses `grievance_core.py`'s exact
  vocabulary (`payment_not_received`, `quality_mismatch`,
  `quantity_mismatch`, `buyer_unresponsive`, `logistics_delay`, `other`)
  rather than the blueprint doc's own list (`PAYMENT_DELAY`,
  `QUALITY_DISPUTE`, ..., `BUYER_BEHAVIOUR`, `PRICE_DISPUTE`). The doc is
  aspirational prose; `grievance_core.py` is tested, running code with 9
  passing tests of its own. This is the same category of
  doc-vs-running-code conflict the project has been catching all along,
  and it's resolved the same way: the enum matches the code that
  actually populates it.
- **`buyer_profiles.target_price_index` / `minimum_grade_accepted`**
  come from `tools/augment_buyer_data.py`, which exists precisely because
  `buyers.json` lacked the fields the matching engine needs — the DB
  schema had to carry that fix through, or it would silently regress the
  moment the app switches from JSON to Postgres.
- **`market_prices.source`** enum values (`AGMARKNET`, `DATA_GOV_IN`,
  `ENAM`, `SYNTHETIC`) are copied verbatim from the blueprint, since this
  one is a plain data-provenance tag rather than application behavior.
  Note `ENAM` exists in the enum for schema completeness only — per
  `AUDIT_REPORT.md`'s own research, e-NAM has no public developer API, so
  no ingestion job will actually write that value yet.

Full column-by-column rationale is in the docstring at the top of
`db/models.py`.

## What was actually tested (and how)

Everything below ran against a **real PostgreSQL 16 server**, installed
and started inside this sandbox for the purpose (not SQLite, not a
mocked connection — several things tested, like the JSONB/array columns
and the transaction trigger, are Postgres-specific and wouldn't
meaningfully test on SQLite):

1. Both migrations apply cleanly to an empty database (`alembic upgrade
   head`) — verified by running it, twice (once during development, once
   from inside the automated test run).
2. All 20 expected tables exist afterward (`test_all_expected_tables_exist`).
3. CHECK constraints actually reject bad data — tried inserting a
   `market_price` with `max_price < min_price` and a `lot` with negative
   quantity; both were rejected by Postgres, not just by application code
   that could be bypassed.
4. Uniqueness (`users.phone`) and foreign-key constraints
   (`lots.farmer_id` against a nonexistent farmer) are enforced by the
   database.
5. The transaction state-machine trigger: creating a transaction in any
   status other than `OFFER_ACCEPTED` is rejected; jumping straight from
   `OFFER_ACCEPTED` to `DELIVERED` is rejected; the full legal sequence
   (`OFFER_ACCEPTED → PAYMENT_INITIATED → LOGISTICS_ARRANGED →
   IN_TRANSIT → DELIVERED → PAYMENT_CONFIRMED → COMPLETED`) succeeds;
   `COMPLETED` is confirmed terminal (any further update is rejected);
   `CANCELLED` is confirmed reachable from any non-terminal state.
6. A full `farmer → lot → offer → transaction → payment →
   logistics_booking → grievance` insert chain succeeds end-to-end — this
   is the blueprint's own "Minimum Viable Demo" loop, exercised at the
   data layer.
7. `db/seed_from_json.py` loads all four existing JSON files with row
   counts that match the files exactly (672 market prices, 100 buyers,
   15 logistics providers, 10 cold storage facilities) and every seeded
   market price is confirmed tagged `SYNTHETIC` (not silently presented
   as live data).
8. Migration reversibility: `alembic downgrade base` followed by
   `alembic upgrade head` round-trips cleanly.

**A real bug was caught by test 8, not assumed away:** Alembic's
autogenerated `downgrade()` drops tables but does not drop the
standalone Postgres ENUM types each `Enum` column creates, so a
downgrade-then-upgrade cycle failed with `type "..." already exists` on
first run. Fixed by adding explicit `DROP TYPE IF EXISTS` statements to
`downgrade()` for all 21 enum types this migration creates, then
re-verified the fix by re-running the same test. This is exactly the
"don't claim something works without running it" standard applied to my
own output, not just the prior session's.

Full suite result: **`python3 -m pytest tests/ -v` → 85 passed** (71
original + 14 new). No regressions in the previously-delivered
components.

## What was NOT done (explicitly out of scope for this component)

- `api_v2.py` is **not** rewired to read/write Postgres — it still reads
  the flat JSON files. Wiring the API layer to the DB is a distinct next
  step, not silently bundled into "build the schema."
- No live Agmarknet/data.gov.in ingestion pipeline (blueprint section
  24's fetcher → validator → normalizer → deduplicator). The seed script
  is explicitly a one-shot demo-data loader, not that pipeline, and says
  so in its own docstring.
- No `locations` table — the blueprint's `users.location_id` implies one
  exists, but the blueprint never defines it. Modeled as a plain text
  field (`location_text`) instead of inventing a table the doc doesn't
  specify; flagged rather than silently resolved.
- Enum types are one-per-column-use rather than a single shared "grade"
  enum reused across `lots.grade`, `quality_grades.grade`,
  `buyer_profiles.minimum_grade_accepted`, `buyer_demands.minimum_grade`,
  `buyer_demands.maximum_grade` (5 separate Postgres ENUM types with
  identical values `A`/`B`/`C`). Functionally correct and tested as such,
  but not the most elegant schema; noted here rather than fixed silently
  since consolidating them is a real (if minor) design decision, not
  just a typo fix.
- Caching layer and security pass remain next in the build order per the
  existing plan — untouched by this component.

## How to actually run this (for the next session, or your teammates)

```bash
pip install -r requirements-additions.txt   # now includes SQLAlchemy, Alembic, psycopg2-binary
export DATABASE_URL="postgresql+psycopg2://<user>:<password>@<host>:5432/<dbname>"
python3 -m alembic upgrade head
python3 -m db.seed_from_json   # optional, populates demo data
python3 -m pytest tests/test_db_schema.py -v   # requires a Postgres role that can CREATE/DROP DATABASE
```
